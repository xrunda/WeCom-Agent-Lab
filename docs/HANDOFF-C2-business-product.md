## 0. 先用三句话对齐

1. **平台层面的仗已经打完了。** 企业微信的机器人进不了外部客户群，这是官方限制，实测也确认了。所以「AI 直接在客户群里说话」这条产品形态**不存在**。
2. **替代方案已经端到端跑通。** 叫 C2：客户在群里说话 → 系统读存档（会话存档，付费能力）→ 生成草稿 → 机器人 1:1 推给员工 → **员工自己复制粘贴到客户群** → 系统回读存档，验证「到底发没发、发对群没有」。
3. **现在的代码是一台能跑的真机，不是产品。** 后台管理界面、多群、多顾问、图片理解、规则引擎、知识库——全都没有。你的任务是把「业务侧该长什么样」设计出来。

**不要做的事**：不要重新论证「机器人能不能进外部群」；不要假设平台有自动发群能力；不要把会话存档当成实时消息流。

## 1. 平台事实：产品设计的硬边界

下表每一条都有实测或官方依据，产品方案必须落在这些约束里。违反其中任何一条，方案就不成立。

| # | 事实 | 依据 | 对产品的硬约束 |
|---|---|---|---|
| F1 | 智能机器人不能进外部客户群（普通模式、API 模式都不行） | M1-B 官方原文 + 真实外部群实测 | 机器人只存在于「员工 ↔ 机器人」1:1 里。**客户永远看不到机器人** |
| F2 | 群消息只能通过「会话存档」读 | 存档 SDK 实测通过 | 读不是实时的，是**轮询拉的** |
| F3 | 存档延迟 **上界 35 秒**（实测） | A6 | AI 回复不可能是秒回。产品叙事要按「分钟级」设计 |
| F4 | 存档只保留 **5 天** | 官方 | 服务必须常驻；宕机超 5 天 = 数据永久丢失 |
| F5 | 存档**按员工人头计费**（当前买了 1 个席位） | 服务版 1 人，至 2027-11-08 | 每个顾问都要买席位。**这是直接的成本模型**：顾问数 × 单价 |
| F6 | 授权是**按员工**的，但记录的是**整段会话** | 实测：`from=wm...` 的客户消息同样在档 | 员工所在的所有群、所有成员的发言都会进存档，不只是员工的发言 |
| F7 | 客户必须**同意存档**，否则不落档 | 官方 + 实测（客户侧收到服务须知） | 需要有「告知并取得同意」的产品流程；不同意的客户无法自动服务 |
| F8 | 存档记录字段只有 8 个：`action / from / msgid / msgtime / msgtype / roomid / text / tolist` | 实测 | **没有群名，没有昵称**。群名要另外调客户群 API 或用配置兜底 |
| F9 | 外部客户（个人微信）的 id 以 `wm` 开头；外部会话的 `msgid` 带 `_external` 后缀 | 实测 | 这是区分「客户」和「同事」的唯一依据 |
| F10 | 单聊 `roomid` 为空串，群聊才有 `wr` 前缀的 `roomid` | 实测 | 群 = 会话的容器，产品的主键是群 |
| F11 | 机器人主动推送用 `template_card` / `markdown` / 文件 / 图片，**不支持 `msgtype=text`** | 实测 | 正文用 `markdown` 承载，客户端看起来仍是文本气泡 |
| F12 | 模板卡片的 `task_id` 必须唯一非空，重复返回 42014 | 实测 | 每张卡要带唯一 id |
| F13 | **卡片按钮点完不会置灰、不会变文案**，卡片是静态的 | 实测 | 员工点完没有任何视觉反馈 → 必须用**文字消息**回执 |
| F14 | 同一机器人只允许一个长连接 | 官方 | 单实例部署；多实例需要额外设计 |
| F15 | 群规模、成员、群名可以从「客户群 API」查（`groupchat/get`），但要单独授权 | 代码已实现，后台未开通 | 群名自动获取需要建自建应用 + 可信 IP + 授权（约 10 分钟后台操作） |

## 2. 当前跑通的是什么（真机验证过）

### 2.1 一句话

> 客户在外部客户群发一句话 → 约 1 分钟内员工的企微私聊里出现「卡片 + 正文」→ 员工长按复制、粘到客户群 → 点「已发送」→ 系统回读存档，10 秒左右告知「✅ 已确认发出」。

### 2.2 真实时间线（员工视角，2026-11-08 实测）

```text
[客户] 在「客户-汪女士-20261108」里说：晚上吃什么
   ↓  存档落库，≤35 秒
[系统] 每 20 秒轮询一次存档，发现这条 wm 开头的客户消息
   ↓  草稿入队
[员工] 企微里机器人发来两条消息：
        ① 卡片
           待回复 · 客户-汪女士-20261108      当前仅此一条
           客户原文：晚上吃什么
           客户    外部客户 9NfOsA · 22:36
           群成员  外部客户 9NfOsA、外部客户 D75oBw、WangXing
           命中规则  archive-trigger
           风险    低
           [已发送]  [忽略]
        ② 正文（纯文本气泡，只有要发出去的话）
           收到您的消息：「晚上吃什么」。营养师稍后为您详细回复。（C2 自动草稿，测试内容）
   ↓
[员工] 长按 ② → 复制 → 切到客户群 → 粘贴 → 发送
   ↓
[员工] 回到机器人，点卡片「已发送」
[系统] 立刻回一条文字：
        已记录「已发送」（客户原文「晚上吃什么」）。
        正在回读会话存档确认：顺利的话 10 秒内出结果；若一直没找到，最迟约 85 秒会告诉你失败。
   ↓  10 秒后首次回读
[系统] ✅ 校验通过：客户原文「晚上吃什么」的回复已在「客户-汪女士-20261108」里找到，这条任务完成。
```

失败路径也验证过（这是 C2 的核心价值）：

```text
[员工] 点了「已发送」，但根本没往群里发
   ↓  10 秒首查没找到 → 每 15 秒重试，共 6 次
[系统] ❌ 没有在「客户-汪女士-20261108」里找到这条正文（重试 6 次）。请确认是否真的粘贴发出去了。
```

即：**「嘴上说发了、实际没发」这件事，系统能抓。** 这是整个方案唯一无法被人工替代的价值点。

### 2.3 员工能感知到的时间常数

| 环节 | 时长 | 来源 |
|---|---|---|
| 客户发言 → 存档可读 | ≤ 35 秒 | 实测上界 |
| 存档轮询间隔 | 20 秒 | `TRIGGER_INTERVAL_MS` |
| **客户发言 → 员工看到卡片** | **约 20–60 秒** | 上两者之和 |
| 点「已发送」→ 首个结果 | 10 秒 | `VERIFY_DELAY_MS` |
| 没匹配 → 判定失败 | 约 85 秒 | 10 + 5×15 |
| 员工忘点「已发送」→ 自动回读 | 3 分钟 | `forgottenAckGraceMs` |
| 未处理 → 机器人提醒 | 15 分钟 | `remindAfterMs` |
| 未处理 → 「升级」 | 60 分钟 | `escalateAfterMs`，**当前只写日志，没人收到通知** |

## 3. 角色与对象

| 角色 | 现状 | 谁的 id | 说明 |
|---|---|---|---|
| **顾问 / 员工** | 只有 1 个（`LiGuang`） | 企微 `userid` | 有存档席位；是机器人私聊的另一端；队列的键 |
| **客户** | 个人微信用户 | `wm...` 开头的 id | 在群里发言，看不到机器人；卡片上只显示 id 后 6 位（如「外部客户 9NfOsA」）甚至没有真名 |
| **客户群** | 主键是 `roomid`（32 位） | `wr` 前缀 | 一个群 = 一个服务对象。存档里**没有群名** |
| **同事** | 存在（群里有内部同事） | 企微 `userid` | 发言同样进存档，当前会被当成「客户消息」触发草稿 |
| **主管 / 管理员** | **不存在** | — | 没有任何管理端、没有改派、没有升级通知对象 |

> 产品要特别注意：**现在系统分不清「客户」「客户家属」「内部同事」**。只要不是顾问本人发的文字，都会被当成客户需求。C2-3-01 就是为这件事挂起的。

## 5. 明确没有实现的（这就是你要设计的空白）

按对产品的影响从大到小排：

| # | 空白 | 现状 | 为什么重要 |
|---|---|---|---|
| G1 | **图片 / 文件 / 语音完全不处理** | 适配器直接丢弃 `msgtype !== 'text'` | 健康/饮食服务里，客户发照片大概率是**主要**交互方式。现在发照片 = 系统完全没反应 |
| G2 | **没有业务规则引擎 / 知识库 / 病例 / 菜单** | `compose` 是回显占位 | 产品的核心价值在这里，草稿质量 = 产品质量 |
| G3 | **多群未支持** | 只绑定 1 个群（`ARCHIVE_ROOM_ID`） | 顾问手上有 18 个群。全量采集 + 业务判定是 C2-3 的主题 |
| G4 | **没有「哪些群算客户群」的判定** | 员工在的所有群都进存档、都可能触发 | 私人群、同事群、售前群也会触发草稿。**必须先判定** |
| G5 | **没有管理端 / 工作台** | 配置靠环境变量，状态靠 `~/c2.log` | 谁在服务哪个客户、队列多长、谁被暂停了，全都看不见 |
| G6 | **只有一个顾问** | 顾问表是「存档里第一个说话的人」推断出来的 | 多顾问、排班、改派、离职交接都没有 |
| G7 | **数据不持久** | `MemoryStore`，进程重启全丢 | 重启后所有草稿消失（旧卡片点击会回「卡片已过期」） |
| G8 | **停机期间的消息永久丢失** | 启动时 `startedAt = now`，只处理启动之后的 | 服务挂 10 分钟，这 10 分钟的客户消息不会有草稿，且不会补 |
| G9 | **一条不理的草稿会永久堵住该顾问的队列** | 串行队列「不自动跳过」 | 设计上是为了安全，但产品必须有出口（超时转人工 / 改派 / 放弃） |
| G10 | **「升级」只写日志** | `ESCALATED` 告警只打日志 | 60 分钟没人处理，实际上没有任何人知道 |
| G11 | **群名靠猜** | `GROUP_NAME` 环境变量 / 成员拼接 | 卡片上可能显示「外部客户 9NfOsA、WangXing」而不是「客户-汪女士」 |
| G12 | **客户没有真名** | 存档无昵称，只有 `wm` id | 员工在卡片上看到的是「外部客户 9NfOsA」 |
| G13 | **判失败后不能补校验** | `UNVERIFIED` 是终态 | 员工晚几分钟补发，系统不会再认 |
| G14 | **日志会打出聊天正文** | 每条存档记录打 20 字预览 | 放开全量采集前必须脱敏，否则私人群内容进日志（合规风险） |

## 6. 三个接缝：业务侧只需要接三处

平台细节都封在适配器里，业务侧替换这三处即可，**C2 的编排、队列、校验都不用改**。

| 接缝 | 代码位置 | 现在是什么 | 业务侧要换成什么 |
|---|---|---|---|
| **生成草稿** | `src/c2/trigger.ts` 的 `ComposeFn`，实现在 `live-e2e.ts` 的 `composeReply` | 回显客户原话 | 真正的规则引擎 / 知识库检索 / 模型生成，产出 `body` + `inboundSummary` + `riskLevel` + `ruleIds` |
| **顾问名单** | `live-e2e.ts` 的 `resolveAdvisor` | 从存档里推断「第一个说话的人」 | 业务系统的顾问表（含归属、状态、席位） |
| **校验与告警的去向** | `live-e2e.ts` 的 `verifyMessage` / `onAlert` | 机器人发一句话 / 打日志 | 业务侧的通知、工单、看板 |

`ComposeFn` 的契约（业务侧最重要的一条接口）：

```ts
type ComposeFn = (input: { group: CustomerGroup; message: ArchivedInbound })
  => { body: string; inboundSummary?: string; customerName?: string;
       riskLevel?: 'low' | 'medium' | 'high' } | undefined;
// 返回 undefined = 这条消息不值得回复（静默跳过）
```

## 7. 待产品决策的开放问题

按紧急度排。带 ⏸ 的是**已明确挂起、等业务方答复**的。

### 7.1 ⏸ 判定契约：什么样的群才走服务流程（C2-3-01）

两个候选，语义二选一：

```ts
// A：只看群 —— 这个群是客户群就服务
isServiceable(roomId: string): boolean

// B：群 + 说话的人 —— 同一个群，客户本人和家属区别对待
isServiceable(roomId: string, senderId: string): 服务等级
```

已确认「A 是 B 的退化」，所以签名按 B 写不会白费。**待业务方答复的问题**：

1. 群里通常有谁？只有客户本人，还是家属/同事/助理也常发言？
2. 家属代问（「我妈今天血压高怎么办」）算不算服务请求？
3. 一个客户会有几个群？（现用群名带日期 `客户-汪女士-20261108`，像一次性建的）
4. 非付费客户的群（售前群、同事群）怎么处理 —— 「采集但不服务」还是「根本不看」？后者存档做不到，只能靠判定过滤。
5. 顾问会同时在几个客户群？串行队列在群多起来后能否承受延迟？

### 7.2 一条草稿没人理，怎么办（G9）

现在的答案：永远堵着。产品必须给出口。可选：超时自动转人工 / 改派给主管 / 标记放弃并记录 / 按风险分级（高危不放过，低危可跳过）。

### 7.3 图片怎么办（G1）

客户发一张餐盘照片，是最典型的场景。存档能拿到媒体 `sdkfileid`（需分片拉取），但**当前完全没接**。需要产品定义：图片要不要触发草稿、识别失败怎么降级、员工看到的是什么。

### 7.4 停机补偿（G8）

服务重启后，停机期间的客户消息不会有草稿，且不会补。要不要补？补的话可能一次性涌出几十条草稿。

### 7.5 群与客户的主键关系（C2-3-02）

需要一个「客户 ↔ 群 ↔ 建档状态」的映射表，作为判定的唯一数据源。要定：一对一还是一对多；换群/换顾问怎么处理；签约、停用、过期如何实时生效。

### 7.6 风险分级怎么用

`riskLevel` 字段已经有了（低/中/高），卡片上会显示，但**没有任何行为差异**。高危消息是否要绕过串行队列直接找人？是否禁止 AI 生成只允许人工写？

### 7.7 员工端体验的天花板

员工现在要做的事：切到私聊 → 长按 → 复制 → 切群 → 粘贴 → 发送 → 切回 → 点按钮。**7 步**。产品要评估这个操作成本能不能被顾问接受，以及有没有减少步骤的空间（平台层面已经没有自动发群的路了）。

## 8. 合规与安全（不是可选项）

| 事项 | 现状 | 产品必须处理 |
|---|---|---|
| 客户同意存档 | 客户会收到「服务须知」，同意后才落档 | 不同意存档的客户无法自动服务，退化为纯人工 —— 产品要定义这个降级路径 |
| 员工知情 | 存档按员工授权，员工所在**所有群**都会被采集 | 制度上一般需要书面知情；员工私人群也可能被采集，这是敏感的 |
| 日志正文 | `describeRecord` 对每条记录打 20 字预览 | 放开全量采集前必须先脱敏（C2-3-04） |
| 健康内容 | PRD 明确：不诊断、不调药、不承诺疗效 | 规则引擎和生成层必须内置这条 |
| 数据留存 | PoC 默认 90 天，未实现 | 留存期与删除策略待定 |
| 审计 | 每个动作都写 `audit_event`（内存） | 生产需要持久化 + 可查询 |

## 9. 术语与 id 形态速查

| 名词 | 说明 |
|---|---|
| 会话存档 | 企微付费能力，按人头授权，按员工采集**整段会话**。C2 的唯一读入口 |
| `roomid` | 群的唯一 id，32 位，`wr` 前缀。单聊为空串 |
| `wm...` | 外部联系人的个人微信 id。区分「客户」的唯一依据 |
| `_external` | 外部会话消息 `msgid` 的后缀 |
| `chatid` | 机器人推送的目标；单聊里就等于员工 `userid` |
| 卡片 / 正文 | C2 的两段式消息：卡片放上下文和按钮，正文只放要发出去的话 |
| 串行队列 | 每顾问同一时间只有一条未处理草稿，确认后才推下一条 |
| `VERIFIED` | 存档里在目标群找到了正文（且基本一致） |
| `EDIT_SENT` | 找到了，但员工改过内容 |
| `MISROUTE_ALERT` | 在**别的群**找到了 → 发错群了 |
| `UNVERIFIED` | 约 85 秒内六次回读都没找到 → 大概率没真发 |
| `ADVISOR_PAUSED` | 连续 2 次错群，该顾问被暂停 |

## 10. 现状 vs 目标形态（差距一页纸）

| 维度 | 现在（PoC） | 目标（业务产品） |
|---|---|---|
| 群 | 硬编码 1 个 | 员工名下所有群，业务判定后决定服务哪些 |
| 顾问 | 1 个，靠推断 | 顾问表 + 席位 + 归属 + 状态 |
| 内容 | 只处理文字 | 文字 + 图片（+ 文件/语音视需要） |
| 草稿 | 回显原话 | 规则引擎 / 知识库 / 模型生成 |
| 存储 | 内存，重启即失 | 持久化 |
| 管理 | 环境变量 + 日志文件 | 管理端：群、顾问、队列、告警、审计 |
| 队列出口 | 无，永久阻塞 | 超时 / 改派 / 放弃，按风险分级 |
| 升级 | 写日志 | 通知到具体的人 |
| 判定 | 无，见谁信谁 | `isServiceable` 契约 |

## 11. 建议你（接手方）先产出这三样

1. **判定契约的产品定义**：把 §7.1 的 5 个问题变成明确的业务规则，能直接写成代码（谁可以被服务、什么条件下、失效怎么处理）。
2. **员工端一次完整对话的体验稿**：从「客户发来一张照片」到「员工点完按钮」，逐帧写清楚系统说什么、员工做什么、错了会怎样。这能暴露 §7.7 的 7 步操作是不是可接受。
3. **管理端最小信息架构**：群与客户怎么看、队列堵了怎么发现、谁被暂停了怎么恢复、每月的席位成本怎么算。

写完后对着 §1 的 F1–F15 逐条检查一遍——凡是需要「机器人自动发到客户群」的设计，一律不成立，要改。
