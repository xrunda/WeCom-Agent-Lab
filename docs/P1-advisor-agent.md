# P1 顾问 Agent（企微 1:1 自由问答）

> 状态：设计稿，未开发
> 关联：#162（固定指令）、#163（1:1 只发聚合提醒）、#146（待回复索引）
> 前置阅读：[P1-patient-agent.md](P1-patient-agent.md)、[P1-M0-dsh-validation.md](P1-M0-dsh-validation.md)

## 1. 为什么要做

现在的机器人是一组**精确匹配的指令**：`话术 …`、`知识 …`、`我的待办`、`为什么红线`。
每加一种问法就要加一条正则，问法一变就退化成「用法：收到草稿后直接回复一句话…」。

真机案例：顾问粘贴质检提醒后问「为什么警告?」——因为词表里只有「为什么红线」，
机器人把它当成改稿指令，回了用法提示。这不是文案问题，是能力边界问题：
**顾问认为自己在跟一个 Agent 说话，系统却在做关键词路由。**

目标：DSH 作为顾问的 Agent 真正接管 1:1 对话。顾问用自己的话随便问，
Agent 通过**只读工具**查本人名下的真实数据后回答；需要改稿时调用改稿工具，
仍然由顾问确认发送。

## 2. 目标与非目标

**目标**

- 自由文本即可问：客户情况、待办、草稿、红线、群动态、知识库、话术
- 回答必须基于工具返回的事实；查不到就说查不到，不编造
- 身份由会话绑定，工具参数里不接受 advisorId，杜绝越权
- 客户昵称仍按 `patient.read` 收口；日志不含正文
- 模型失败 / 未授权时有确定性的降级路径，不是静默失败

**非目标（本期不做）**

- Agent 不向客户群发送任何消息，也不替顾问点「确认发送」
- 不做诊断、不给用药剂量、不承诺疗效（沿用患者侧红线）
- 不改病历、不改慢病档案（写入类工具后续单独评估）
- 不做跨顾问 / 跨租户查询；主管视角另立工作包

## 3. 总体架构

```
企微 1:1 文本
   │
   ▼
zhiban-wecom（传输 + 路由）
   │  ① 精确命令（帮助 / 重置对话 / 我的待办 / 编号选择）
   │     —— 整条消息等于命令才走，秒回、零模型成本
   │  ② 其余全部 → zhibanAdvisor
   ▼
zhiban-advisor（新插件：会话 + 编排 + 工具）
   │  advisorId ← 企微 userid（会话绑定，不接受入参）
   │  每顾问一条 DSH 长期会话 zhiban-advisor-<advisorId>
   ▼
DSH Agent（只含业务工具的 preset + 工作区 AGENTS.md 人设）
   │  调用只读工具（全部走 ctx.get 拿其他插件的只读接口）
   ▼
session/event → assistant/message → turn/end
   │
   ▼
bot.sendText(顾问 userid)  ← 拆条后回复
```

关键点：

- **一位顾问一条会话**。顾问的问题是跨客户的（「汪女士最近血糖」「今天有啥要处理」），
  不能塞进患者会话。
- **工具是唯一的数据入口**。Agent 不直接读库，工具内部做顾问范围过滤与字段裁剪。
- **回复从会话事件里取**，不要求模型额外调一个「回复」工具（见 §5 Spike）。
- **命令与 Agent 不是两套能力**：命令只是少数几个确定性动作的快车道，用户问「知识库」
  「话术」这类问题只走 Agent（工具），不再用关键词匹配（见 §9）。

## 4. 会话模型

- id：`zhiban-advisor-<advisorId>`，工作区 `/var/lib/zhiban/advisors/<advisorId>`
- 会话记录存 `zhiban-advisor` 自己的 domain（advisorId → sessionId / workspacePath）
- 长期复用；DSH 自带压缩，不为每轮重建
- 「重置对话」：在新会话里才能摆脱跑偏的上下文。任何顾问发 `重置对话` 时
  `reset()` → 新建会话并覆盖记录，回执「已清空上下文」；旧会话不再复用
- 重启后 sessionId 稳定（P1-M0 已验证），插件启动时校验 `resolveAgent`，
  取不到就重建并记一条告警

## 5. 回复捕获（G1：Spike 决定）

DSH 会在会话上发出 `session/event`，包含 `turn/start`、`assistant/message`、
`tool/result`、`turn/end`（在 dsh-session 的类型里已确认存在）。
插件可以像 `ctx.on('tools/result')` 一样订阅。

**首选方案（事件捕获）**

```
prompt(session, turnPrompt)
  ├─ turn/start            记录 turn 号
  ├─ assistant/message     累加文本；含 tool call 的中间步不当作最终回答
  ├─ turn/end(completed)   取最后一条纯文本 assistant/message 作为回复
  └─ turn/end(其他)        降级文案 + 保留可用指令提示
```

需要 Spike 确认三件事：

1. `ctx.on('session/event', (session, event) => …)` 在插件里可用，且能按 sessionId 过滤
2. 一轮里多次 `assistant/message`（工具前后）能区分「中间态」与「最终答案」
3. 中断 / 超时的 turn 也能拿到已产出的文本前缀（`interrupted: true`）

**备选方案（回复工具）**：注册 `advisor_reply({ text })`，人设要求每轮必须调用，
就像患者侧的 `reply_draft`。确定性最好，但要求模型守约定，且多一次往返。
Spike 若证明事件方案不可用，直接落到备选，不阻塞排期。

## 6. 回合编排

```
onText(advisor, text):
  if 聊天室未就绪 → 回执「机器人还没连上」
  if 该顾问有进行中的回合 → 回执「上一条还在处理，稍等」
  if 触发限流 → 回执剩余等待秒数
  session = ensure(advisor)
  turnPrompt = persona.turnPrefix(advisor, snapshot()) + "顾问问题：\n" + text
  prompt(session, turnPrompt)
  等 turn/end（超时 30s）
  成功 → 拆条发送 assistant 文本（企微 markdown，≤2000 字节/条）
  超时但后来完成 → 仍发送，前缀「刚才那条查完了：」
  失败 → 发送降级提示（§8）
```

**每轮前置上下文**（不额外调工具就能知道"现在什么情况"）：

```
[知伴 · 顾问助理] 顾问：王顾问（adv_1）｜2026-11-14 10:32（上海）
今日：未完成草稿 2（最久 3 天）· 今日到期承诺 1 · 未处理告警 2 · 待回复会话 3
活动草稿：draft_38 ·「客户-汪女士-20261108」· 第 2 版 · 中风险
顾问问题：
```

前置上下文只放计数与当前活动草稿的元数据，不放客户正文。

## 7. 工具清单

所有工具：`execute(args, exec)` 用 `exec.agent.id` 反查 advisorId，**参数里没有身份字段**；
返回结构化 JSON（DSH 自动转成工具结果文本），逐项限制条数与字段。

### 7.1 v1 工具（第一版就注册）

第一版只注册**最常用的六项**。工具越多，模型选错的概率越高，评测成本也翻倍；
其余工具按真实提问日志补（见 §14）。

| 工具 | 数据源 | 返回 | 上限 / 说明 |
|---|---|---|---|
| `advisor_todo` | 草稿 + 承诺 + 告警 + 待回复 | 四类计数、最久等待、最近一条标题 | 无参；与「我的待办」命令共用同一个格式化函数 |
| `patient_chronic` | `getChronicProfile()` | 疾病、最近 3 条体征、用药、更新时间 | 需 `patient.read`；无档案时明确回「无记录」 |
| `knowledge_search` | `zhibanKnowledge` | 命中条目的 id、标题、**原文** | 最多 5 条；未命中返回空列表，不造条目 |
| `knowledge_get` | 同上 | 单条全文 | 按 id 取；编号选择也落到这里 |
| `script_search` | `zhibanScripts` | 话术标题、摘要、原文 | 最多 5 条；与现有话术库同源 |
| `script_get` | 同上 | 单条全文 | 按 id 取 |

**原文照抄**：知识、话术、红线解释一律由工具返回机构原文，模型只做「找到 + 排版」，
不得改写、合并、概括，也不得在未命中时凭常识补一条。评测里按「返回文本必须与库内
原文完全一致」判定（§13）。

### 7.2 后续按日志补（不进 v1）

| 工具 | 数据源 | 触发补充的条件 |
|---|---|---|
| `advisor_pending` | `zhibanSidebar.allItems()` | 日志里出现「谁在等我 / 哪条还没回」且现有工具答不全 |
| `advisor_drafts` / `advisor_draft_get` | `zhibanAdvisorData` | 顾问要求列出/展开本人草稿清单 |
| `advisor_redline` | `zhibanGuard.alerts()` + `getRule()` | 需要一次性列出多条红线提醒时 |
| `patient_search` | `zhibanPatient.listPatients()` | 无法定位患者（只有名字片段/标签）时 |
| `group_activity` | `zhibanPatient.listGroups()` | 问群动态、活跃度时 |
| `patrol_status` | `zhibanWecom` 巡检状态 | 问巡检/信号时 |

**补充方式**：每两周看一次未命中工具的日志（只记工具名与失败原因），按频次排序补，
不预先造全量工具清单。

### 7.3 写入（Phase 2）

| 工具 | 行为 | 边界 |
|---|---|---|
| `draft_revise` | `{ draftId?, instruction }` → 转给**既有改稿路径**，返回新版本号 | 只能改本人草稿；仍需顾问确认发送；不新建与患者会话联动的第二套改稿 |

v1 不注册 `draft_revise`：1:1 里已有改稿链路，Agent 先把「改稿」意图识别出来再决定是否接入。
过渡期由人设指引「要改稿请直接回复草稿」——这与现有行为一致，不丢能力。

### 7.4 绝不注册

- 向客户群 / 客户单聊发消息
- 确认发送、撤回、转交
- 改患者档案、慢病档案、同意状态
- 跨顾问查询（含主管视角）

## 8. 人设与提示词

放在顾问工作区 `AGENTS.md`（由插件启动时写入，来源 `src/p1/advisor/persona.ts`）：

- 身份：你是「知伴」给**顾问本人**用的助理，回答直接给顾问看，不会发给客户
- 事实优先：先调工具再回答；工具没返回的不要推测；区分「档案里有的」与「我推断的」
- **机构原文照抄**：知识库、话术、红线条款必须原样引用工具返回的文本，不得改写、
  合并、概括、换措辞；引用时带条目 id。规则要求「怎么跟客户说」时，给原文，不给转述
- **不得编造机构知识**：工具返回空就是没有，直说「知识库里没找到」，最多列出相近条目，
  不许凭常识补一条
- 时间与来源：说清数据时间（如「11-12 空腹 6.8」）
- 查不到：给出下一步（「这个患者没有慢病档案，可以在控制台补录」）
- 权限不足：直说没有权限，不提示别人的信息
- 长度：企微单条 ≤900 字，先结论后明细；需要时给 3–5 条要点
- 工具调用上限：每轮 8 次；拿不到就停，别反复试
- 改稿：只有明确在要求改稿时才处理；改完说明版本号，提醒仍需确认发送
- 红线：沿用患者侧条款——不诊断、不调药量、不承诺疗效、急症先建议就医

**降级文案**（模型超时 / 报错 / 无回复）：

```
我这边暂时没接上模型，先把能确定的给你：
· 我的待办 —— 未完成草稿、今日承诺、未处理告警
稍后可以再问一次。
```

降级只保留仍在命令表里的动作，不列已退役的关键词（否则等于把词表又教给用户）。

## 9. 路由与兼容

`plugins/zhiban-wecom/index.ts` 单聊文本：

1. 精确命令（整条消息等于命令，且处于对应状态时才命中）→ 秒回
2. 其余全部 → `zhibanAdvisor.handle()`
3. `zhibanAdvisor` 未安装 / `enabled=false` / 该顾问额度用尽 → 回到旧路径
   （有活动草稿当改稿，否则用法提示）

**命令表（闭集，不再扩充）**

| 命令 | 类型 | 理由 |
|---|---|---|
| `帮助` | 静态文案 | 新顾问入口；模型不该承担「你能做什么」 |
| `重置对话` | 会话动作 | 清上下文是系统权限，不给模型 |
| `我的待办` | 取数 + 格式化 | 最高频、要求秒回与确定性；Agent 可用 `advisor_todo` 回答同一问题 |
| 纯编号 `1`…`9` | 选择上一条列表 | 状态型操作；让模型数「第几条」不可靠 |

知识、话术、为什么红线、我的草稿**全部退役为 Agent 工具**，不再保留关键词路径。

**三条硬规则**

1. **精确匹配**：不做「包含关键词」，不猜意图。问法变化由 Agent 承担。
2. **不因识别失败加词**：任何一次「答非所问」都以补工具、改人设解决，
   禁止往命令表加正则。命令表只允许变短。
3. **同一问题同一个答案**：`我的待办` 命令与 `advisor_todo` 工具共用同一个
   格式化函数（`src/p1/advisor/format.ts`），避免两边数字或措辞不一致。

`advisorStatus` 保留为 `我的待办` 的实现在与降级来源；`knowledgeQuery` /
`scriptQuery` 的检索逻辑迁到工具里复用（不复制一套匹配算法），原 service 若无其他调用方则删除。

配置开关（`zhiban-advisor` 插件行）：

```json
{
  "workspaceRoot": "/var/lib/zhiban/advisors",
  "agentPreset": "zhiban-advisor",
  "turnTimeoutMs": 30000,
  "maxConcurrentTurns": 2,
  "messagesPerMinute": 20,
  "messagesPerDay": 500,
  "enabled": true
}
```

- `agentPreset` 待 Spike 决定：能复用默认 preset 就不新增 profile 行；
  **但会话可见的工具必须只有 §7.1 的业务工具**，不得带文件读写 / shell
- 全机构开放（2026-11-14 决定，不做 pilot 名单）
- 修改 profile 前先备份（`cordis.patch.yml` 含凭据，不打印、不提交）

## 10. 权限与隐私

| 项 | 规则 |
|---|---|
| 身份 | 会话 id → advisorId 唯一映射；工具忽略任何身份入参 |
| 数据范围 | 只返回 `advisorId` 匹配的草稿 / 承诺 / 告警 / 群 / 患者 |
| 客户昵称 | `patient.read` 才给；否则 id 尾号 |
| 日志 | 只记 advisor 尾号、回合耗时、工具名、成功/失败；不记提示词、工具参数、工具结果、回复正文 |
| 会话文件 | DSH 会把对话写到 `DSH_HOME/sessions`（含工具结果），沿用患者会话的磁盘权限；保留期与清理策略进 v2 |
| 评测 | 只用虚构数据；真机验证单列，不写进离线报告 |

## 11. 失败与降级

| 情况 | 行为 |
|---|---|
| 模型超时（30s） | 回「这个问题要久一点，我查完直接发你」；回合结束后仍发送结果 |
| 模型报错 | 降级文案（§8）+ 日志记错误码 |
| 取不到工具数据（插件未装） | 工具返回空 + 说明，Agent 据此回答「这项还没接入」 |
| 回合产出为空 | 「这次没查到能回答的内容」，不编造 |
| 顾问连发多条 | 单顾问串行；进行中再发 → 「上一条还在处理」 |
| 全局并发满（2） | 排队 5s，仍满则提示稍后再问 |
| 重启 | 会话续用；进行中的回合丢失，回执「刚才那条中断了，请再发一次」 |

## 12. 成本与容量

- 单轮预期：1–3 次模型调用（工具前后），输入 2–4k tokens，输出 <800
- 2GB VM：`maxConcurrentTurns=2`，单顾问串行；全机构上线前先做 10 轮连续问答压测
- 每顾问每分钟 20 条、每天 500 条上限；超出回执剩余时间
- 上线前在 VM 上压测：10 轮连续问答的 P50/P95 与内存水位

## 13. 测试与验收

**单元（离线，虚构数据）**

- 工具参数校验、身份绑定、范围过滤、字段裁剪、昵称权限
- 路由：快捷指令 / Agent / 降级三条路径
- 包装配：`ctx.get` 缺插件时的安全降级

**评测（真 DSH + 假数据）**

- `eval/advisor/cases/*.json`：v1 8 条，覆盖待办、患者慢病、知识命中、话术命中、
  知识未命中、权限不足、越权、改稿意图；后续按日志补到 20 条
- 判定：命中预期工具与字段；不得出现其他顾问的数据；不得出现客户原文（除顾问自己的草稿）
- **原文一致性**：知识与话术的返回文本必须与库内原文逐字相等（防止模型改写）

**真机（企微）**

1. 粘贴质检提醒后问「为什么警告?」→ 解释规则
2. 「汪女士最近血糖怎么样」→ 调 `patient_chronic`，带时间与数值
3. 「今天有什么要我处理的」→ 汇总，数字与跑一次「我的待办」命令完全一致
4. 「降压药的话术再发我一遍」→ 调 `script_get`，返回话术原文（逐字一致）
5. 「帮我把刚才那条改温和点」→ v1 指引回草稿确认（v3 起由 Agent 直接改稿）
6. 换一位未授权的顾问问同一患者 → 只回无权限

**验收口径**：真机通过才写「已通过」；mock / 评测通过只写「离线通过」。

## 15. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 工具结果过大 | 上下文膨胀、变慢 | 每个工具硬上限 + 摘要优先，详情按 id 再查 |
| 模型改写机构原文 | 医疗口径失真、合规事故 | 工具返回原文 + 人设禁止改写 + 评测逐字比对（§13） |
| 命令与 Agent 答案不一致 | 顾问不信任数字 | 共用同一格式化函数（`src/p1/advisor/format.ts`），验收里比对两路口径 |
| 词表回潮 | 又回到「加一条正则」的老路 | §9 硬规则：命令表只允许变短；答非所问一律记 issue 补工具 |
| 模型误判改稿 | 该回答时改了稿 | 人设明确「先判断意图」；改稿仍走既有确认链路 |
| 越权 | 数据泄露 | 身份只从会话解析；单测覆盖「参数伪造 advisorId 被忽略」 |
| 会话文件含正文 | 合规 | 磁盘权限沿用；保留期与清理进 v2；日志仍不落正文 |
| 2GB VM 撑不住 | 卡顿 / OOM | 并发 2、压测前置 |
| 成本不可控 | 账单 | 每分钟/每天上限 + 用量日志（只记 token 数） |

## 16. 已确认口径（2026-11-14，issue #167）

| 项 | 结论 |
|---|---|
| 快捷指令 | **收窄为精确命令**：帮助 / 重置对话 / 我的待办 / 编号选择；知识、话术、为什么红线、我的草稿全部退役为 Agent 工具 |
| 命令表纪律 | 只允许变短；不因识别失败加词（「为什么警告」类问题靠补工具解决） |
| 知识 / 话术 | 由 `knowledge_search/get`、`script_search/get` 工具返回**机构原文**，模型不得改写；未命中如实说没找到 |
| 命令与 Agent 一致 | `我的待办` 命令与 `advisor_todo` 工具共用同一格式化函数 |
| v1 范围 | 6 个只读工具（待办 / 慢病 / 知识 / 话术），不含改稿工具与全量工具 |
| 灰度 | 全机构，不做 pilot 名单 |
| 用量上限 | 每顾问每天 500 条 |
| 会话保留 | 沿用 DSH 现有会话保留 +「重置对话」 |
| 改稿 | 允许 Agent 改稿；发送仍由顾问确认；v1 先沿用既有改稿链路 |
