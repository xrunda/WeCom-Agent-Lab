## 2. 前置条件

### 2.1 环境与账号

| 项 | 要求 | 检查方式 |
|---|---|---|
| 环境 | `ZHIBAN_ENV=demo`，演示机器人，独立 `DSH_HOME` | `dsh --profile zhiban-demo --dump-config` 查看 `environment` |
| 存档席位 | 当前唯一的存档席位顾问必须在每个演示群内 | 企微群里能看到该顾问 |
| 测试号 | 至少 3 个个人微信测试号（下称 A / B / C），轮流扮演患者与家属 | 能分别加入测试群并发言 |
| 测试群 | 8 个客户群，群名即虚构患者名；每群只有「1 个测试号 + 存档顾问」 | 群成员列表 |
| 存档同意 | 每个测试号在每个群完成会话存档同意 | 企微提示 / 控制台同意状态 |
| 群白名单 | 8 个群 roomid 全部写入 `zhiban-wecom` 的 `serviceGroupRoomIds` | profile 配置（只查路径，不打印 Secret） |
| 演示标记 | `zhiban-patient` 配置 `demo: true` | 控制台患者卡出现「演示」标签 |
| 图片链路 | #55 已合并并在 demo 实例加载 | 沙盒先发 1 张图确认能出草稿 |

### 2.2 已知阻塞（执行前必须解决）

1. **群状态入口已补齐（本 PR 后可用）。** 群被存档发现后默认 `pending`，只有 `serving`
   会触发患者 Agent 回合。现在有两层入口：
   - 控制台 API：`GET /zhiban/api/groups`、`PATCH /zhiban/api/groups/{id}`
     （`{ name?, status?, advisorId? }`，需 `patient.write`）；
   - 运维脚本：`npm run group:status -- --list` 查看，
     `npm run group:status -- --room-id <roomid> --status serving` 改状态。

   脚本只调控制台公开接口，不直写数据库；账号密码走 `ZHIBAN_CONSOLE_USERNAME` /
   `ZHIBAN_CONSOLE_PASSWORD` 环境变量，不会打印。先用 `--dry-run` 确认匹配到的群唯一，
   再正式提交。真实生效仍需 demo 实例加载本 PR 后的版本——**本地单测不能替代真机确认**。
2. **同意状态已接入自动同步（⏳ 待真机）。** `zhiban-wecom` 按 roomid 调
   `check_room_agree` 刷新成员与患者状态（见 [P1 患者 Agent §4](./P1-patient-agent.md)）；
   真机确认前，播种仍应逐群核对状态为 `agreed` 或 `unknown`
   （`requireConsentForTurn=false` 时 `unknown` 可服务；`disagreed` 永不服务）。
3. **原图转推依赖 #55 真机验证。** 若企微图片消息发送失败，图片回合仍会出草稿，
   但服务群收不到原图；此时把「图片转发」记为 ❌/⏳，不要把草稿成功当成转发成功。

## 4. 对话剧本

### 4.1 Day 0：准备（约 60–90 分钟）

1. 建 8 个群，群名与患者名一致；每群拉入对应测试号和存档顾问。
2. 用测试号逐群完成存档同意。
3. 在 demo profile 写入 8 个 roomid 白名单，重启 demo 实例。
4. 用 `npm run group:status -- --list` 核对 8 个群，逐个 `--status serving`（先 `--dry-run`）；
   确认列表里 8 个群均为 `serving`。
5. 控制台确认 8 位患者均带「演示」标签，且每人已有独立 Session。
6. 先做一次冒烟：陈嘉禾群发「你好」，确认顾问 1:1 收到卡片。

### 4.2 Day 1 上午：控糖、减重、夜班

#### 患者 1 · 陈嘉禾（测试号 A）

| 顺序 | 发送内容 | 预期 |
|---|---|---|
| 1 | 文字：「我一般晚上七点半吃饭，最近餐后血糖有点高，晚饭该怎么搭配？」 | 建立记忆「晚餐约 19:30」；草稿给搭配建议，风险 low |
| 2 | 图片：自制的虚构餐食照片（清蒸鱼 + 半碗米饭 + 西兰花） | `image_classify` 返回 `meal`；写入 1 条饮食记录；草稿提到主要食物，风险 low/medium |
| 3 | 文字：「以后每天晚上八点提醒我测血糖吧。」 | 调用 `schedule_create`；患者主页出现 1 条待执行主动计划 |

**刻意改稿**：顾问在机器人 1:1 发「语气再柔和一点，不要用『必须』，改成建议」。
预期：收到「正在改第 2 版」，新卡片为第 2 版，旧卡片点击提示 `STALE_CARD`。

## 6. 验收数据核对

| 页面/数据 | 期望 | 一致性检查 |
|---|---|---|
| 工作台 | 有草稿、患者、告警、核验统计 | 草稿数与服务流列表一致 |

| 告警 | 何俊 warning、郑伯 critical、错群/未核验可见 | 告警能跳到对应草稿 |

## 8. 重放方法

1. **只操作 demo 环境。** 确认 `ZHIBAN_ENV=demo`、`DSH_HOME` 指向演示目录；不要动 dev 与生产。
2. 备份演示 `DSH_HOME`（含领域存储与媒体目录），记录备份时间。
3. 清空演示租户数据（由项目负责人用受控方式执行；不要直写业务表造数）。
4. 重启 demo 实例，确认 8 个群重新被发现。
5. 按 §4.1 重新把群置为 `serving`、确认同意状态。
6. 从 Day 1 开始照剧本重放；刻意异常按 §5 各做 1 次。
7. 重放不要求逐字一致；患者原话可微调，但**不要**改变消息意图与异常类型。

## 9. 已知限制与缺口

1. **群状态入口已实现、待真机确认**：API 与脚本已随本 PR 提供；在 demo 实例加载新版并
   实际改成一个群之前，仍不能宣称真实播种可开跑（见 §2.2）。
2. **同意状态自动同步待真机**：已接入 `check_room_agree`，但需在 demo 实例确认返回的
   `exteranalopenid` 与成员 `externalUserId` 一致；真机确认前播种仍以控制台显示为准，
   必要时用 `setMemberConsent` 手工修正。
3. **红线关键词误报**：安全表述「不建议自行停药」会命中「停药」，产生 warning。
   本次保留为告警样例；是否改为否定词排除，由红线规则负责人决定。
4. **图片转推**：依赖 #55 的真机验证；图片草稿成功不等于原图送达。
5. **主动计划**：计划创建可立即验证；是否按时触发取决于测试窗口与安静时段，未触发时记 ⏳。
6. **演示标签**：患者卡已支持 `demo` 标签；若某页未展示，以控制台实际页面为准，不手改数据绕过。
7. **一周与人力的取舍**：2–3 天压缩版能产出全部验收数据，但「连续一周」的服务节奏只能靠 Day 4–7 补点模拟。
