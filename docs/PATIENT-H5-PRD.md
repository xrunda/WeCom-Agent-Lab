> 日期：2026-11-24 · 状态：需求初稿，供评审和后续拆分工作包。
> 已确认方向：患者端先采用 H5 落地与验证；以个人健康计划与健康日历为核心；沿用已讨论的温润食养视觉风格。
> 本文中的首期细节为产品建议，尚未全部经业务评审；功能均为待开发、待验收，不代表已经上线。
> 依据：[产品顶层定义](PRODUCT-FOUNDATION.md)、本次患者端讨论及十张概念效果图。
> 与现行范围的关系：患者端直连属于 [现行 PRD](../PRD.md) 和 [P1 范围](P1-scope.md) 之外的新增范围。本文定义 H5 验证版需求，不将其追认为原 P1 已承诺内容；工程实施前单独建 issue、分包、确定契约和验收。

## 1. 产品定义

知伴健康患者端 H5，是患者在微信内使用的个人食养陪伴入口。它将专业指导转化为个性化健康计划与健康日历，通过每日行动、便捷记录、主动跟踪和专业反馈，连接健康理念与日常生活。

**核心价值主张：基于个人健康档案和经专业审核的食养规则，由 AI 自动生成个性化健康计划与健康日历，将计划拆解为每天能理解、能执行的行动；自动提醒、主动跟踪执行情况与身体反馈，让记录更轻松、变化被及时关注，并在需要时转交专业人员处理。**

### 1.1 世界观与文化支撑

- 使命：让专业的食养指导走进每个人的日常生活。
- 本轮补充的方向：健康管理前移。关注饮食、作息与身体反馈，让关怀更早发生、持续更久；结合中医“治未病”思想展开表达。
- 理论与方法：以中医食养为框架，以药食同源为重要支撑，结合现代营养知识和专业指导。
- 对外主张：**食养融入日常，健康关怀更早一点。**
- 胃肠健康等仅为可探索场景，首期不限定病种，不承诺通过食疗消除病变或预防癌症。

### 1.2 H5、企微与后台的分工

| 部分 | 使用者 | 职责 |
|---|---|---|
| 患者 H5 | 患者本人 | 查看计划与日历、记录、反馈、阅读、联系团队 |
| 企微侧边栏与控制台 | 顾问、专业审核人员、主管 | 建立服务关系、审核发布计划、查看记录、处理反馈和提醒 |
| 服务后台与 AI | 系统 | 档案整合、计划生成、日历编排、任务调度、记录整理、风险识别与留痕 |

H5 不要求患者安装企业微信。首期不提供开放式患者 AI 聊天，不以员工账号或员工侧边栏作为患者入口。

## 2. 目标、用户与验证假设

### 2.1 首期目标

验证患者能否理解自己的健康计划、找到今天的行动、轻松记录，并愿意持续回来使用；同时验证专业团队能否接住反馈，让服务形成持续循环。

首期面向已有服务关系、愿意参与试点的成年患者，兼顾中老年用户的大字、清晰操作和低输入负担需求。不依赖特定机构品牌、产品或病种。

### 2.2 角色

| 角色 | 权限与责任 |
|---|---|
| 患者本人 | 查看本人已发布内容；维护生活偏好；提交与更正本人记录；提出调整需求 |
| 负责顾问 | 邀请绑定、协助建档、跟进执行、发送提醒、协调专业处理 |
| 专业审核人员 | 审核食养规则、个性化计划及其变更；处理超出顾问职责的事项 |
| 主管 | 处理无人认领、超时和服务异常；维护服务安排 |
| 内容编辑与审核人员 | 维护食养文章、出处与审核版本；不因此获得全部患者档案权限 |

专业审核是业务职责，不能默认现有管理员或主管角色具备相应资质。人员配置和授权需在试点前明确。家属代管、多患者切换和未成年人首期不做，后续单独设计授权。

### 2.3 核心假设

1. 将方案转成健康日历，有助于患者理解和执行。
2. 拍照与选择式反馈，比复制长日志更容易坚持。
3. 与个人计划相关的食养内容，有助于理解安排与建立信任。
4. AI 整理与主动跟踪，能帮助团队及时发现需要关注的事项。

## 3. 首期范围

本文优先级：**M 必须完成才能真实试点；S 后续增强。** 概念图中的入口与文案不是功能验收证据。

| 模块 | M：首期真实能力 | S：后续增强 |
|---|---|---|
| 进入服务 | 邀请、身份验证、患者绑定、授权说明、退出登录 | 微信授权接入、家属代管 |
| 轻量建档 | 目标、饮食作息偏好、过敏与既有指导确认、缺失信息补充 | 更丰富问卷、设备接入 |
| 健康计划 | AI 生成草稿、专业审核发布、版本与调整申请 | 更细的规则编排与自动化策略 |
| 健康日历 | 今日/周视图、日期切换、事项详情、状态反馈 | 完整月历、系统日历同步 |
| 日常记录 | 餐食图片/文字、确认识别结果、晚间回顾、历史更正 | H5 内录音与转写、更多专项量表 |
| 主动服务 | 提醒任务、频控、顾问发送、反馈处理状态 | 经验证的新消息渠道 |
| 文化内容 | 食养主张、计划解释、日历提示、分类文章与详情 | 搜索、收藏、分享增强 |
| 个人中心 | 档案、记录历史、计划、团队、提醒偏好、隐私入口 | 独立阶段报告、复杂趋势分析 |

### 3.1 首期明确不做

原生小程序、支付商城、产品营销推荐、自动诊断/处方/调药、舌象分析、体检报告自动解读、自动体质诊断、全天候在线问诊、开放式患者 AI 聊天、机器人自动发外部客户群。

十张效果图中的语音按钮、搜索、收藏、分享和阶段回顾入口属于增强项；未接入时隐藏，不放无效按钮，也不使用静态数字伪装真实统计。患者可使用手机输入法语音转文字，作为首期便捷输入方式。

## 4. 信息架构与服务流程

```text
邀请入口 → 身份验证 → 服务与隐私授权 → 食养主张（可跳过）
                                      ↓
                          轻量建档 → 计划准备中
                                      ↓
                         AI 草稿 → 专业审核发布
                                      ↓
患者 H5
├─ 今天：下一项行动 / 今日进度 / 快捷记录 / 相关食养 / 团队入口
├─ 日历：周视图 / 每日事项 / 事项详情与反馈
├─ 食养：主张介绍 / 分类内容 / 文章详情
└─ 我的：健康计划 / 档案 / 记录 / 专业团队 / 提醒偏好 / 隐私与授权

执行与记录 → AI 整理 → 团队跟进 → 必要时形成计划新版本
```

任何页面刷新、后退或从微信重新打开，都需回到有效的身份与业务状态；不能仅因看过引导页就视为建档或计划完成。

## 5. 入口、身份与授权

### 5.1 入口设计

由负责顾问创建邀请，通过现有服务会话发送；患者也可扫描邀请二维码。公开介绍与食养文章可分享，个人计划、日历、记录必须登录。

首期建议采用“短时单次邀请 + 预绑定手机号验证码”建立患者身份；邀请只代表进入资格，不能单凭链接读取个人健康信息。短信供应商及资源待落实。若试点前无法接入，需单独评审替代的独立身份核验方案；演示账号只能使用虚构数据。

邀请需有过期、已使用、撤销、手机号不匹配和无服务权限状态；患者可联系顾问重新办理，不向未认证访问者展示患者姓名或档案。完成认证后使用可撤销的患者会话，不复用控制台或企微员工会话。

### 5.2 授权与服务状态

- 明确说明健康信息用途、可访问的团队、AI 参与范围及撤回方式；用户主动确认，保留授权版本与时间。
- H5 健康信息处理授权和企微会话存档同意分别记录。不同意存档不能被推定为不同意 H5，反之亦然。
- 未授权时可阅读公开内容，个人建档、AI 处理与健康服务按授权范围限制。
- 拒绝、撤回、解绑、服务停用后停止相应 AI 处理和提醒，撤销不再有效的访问；保存、删除与留存依据上线前确定的政策执行。
- 旧患者模型的 `consent` 不能直接充当 H5 的全部授权状态，需在新契约中拆分。

## 6. 页面需求

### H01 食养主张

展示使命、简短说明、食材图像和“饮食有养 / 起居有常 / 健康有伴”。经典引用需标明出处，并配白话解释。主按钮根据状态进入建档或现有计划；允许跳过，之后可从食养栏目回看。

### H02 轻量建档（新增必要流程）

分步了解希望改善的生活习惯、通常用餐与睡眠时间、食物偏好、过敏禁忌及已有专业指导。已有资料让患者确认或申请更正，避免重复输入；不确定的答案允许选“不清楚”。

区分患者自述与专业确认的信息。专业指导和用药等敏感事项不得因患者填写而自动认定为医生结论。关键安全信息不完整或存在冲突时，先补充询问或交团队处理，不生成可执行的个性化建议。

### H03 今天首页

首屏展示问候、当前日期、下一项行动与主要按钮；继续展示今日进度、快捷记录、相关食养和团队入口。

进度只统计当天已发布计划中的行动；自由记录不自动增加分母。无计划时显示“正在为你准备计划”及建档/联系入口；全部完成时给温和回顾，不继续催办。没有适配内容时不强行推荐。

### H04 我的健康计划

展示阶段目标、起止日期、食养思路、本阶段重点、主要行动、专业团队、发布时间及版本。周期由方案决定，效果图中的“28 天”仅为示例。

“为什么这样安排”说明所依据的个人目标、习惯与已审核原则，不展示内部提示词。“查看健康日历”进入执行；“计划不适合”提交带计划版本的调整申请。

未发布草稿对患者不可见；审核状态和人员名称必须来自真实记录。患者确认“已了解计划”可留痕，但不替代专业审核。

### H05 健康日历与事项详情

默认今天、周视图切换日期，区分过去、今天和未来。事项显示时间、行动、简短目的、状态和入口；详情补充执行方式与反馈方式。复查等专业安排仅来自已确认指导，AI 不自行决定检查周期。

| 状态 | 含义与操作 |
|---|---|
| 待进行 | 未来或尚未反馈；可查看说明 |
| 已完成 | 患者明确确认，或关联记录满足该事项的记录要求；可更正 |
| 今天没做到 | 患者主动选择，可补充原因；不作为批评性提示 |
| 需要帮助 | 患者提出困难，生成团队跟进事项 |
| 已取消 | 因计划调整等原因取消，保留历史依据 |

“到期未反馈”是待跟进标记，不能自动写成“未执行”。历史补记保留执行日期和提交时间，禁止提前确认未来行动完成。查看了事项、提醒已发出均不等于行动完成。

### H06 餐食记录

选择餐次与发生时间，拍摄或上传一张餐食图片，也可只填文字；AI 识别候选食物，由患者确认、删除或补充。识别结果、患者确认结果与来源分开保存。

允许选择大致份量和补充感受；首期不输出未经确认的精确热量、营养素或诊疗建议。识别失败或服务超时仍允许手工保存，避免阻塞记录。

保存后明确成功状态和关联日历事项；同一请求重试不重复创建。历史记录可更正，保留版本。照片权限拒绝、上传失败时提供文字入口。

### H07 晚间回顾与身体反馈

选择整体感受、心情和昨晚睡眠情况；可展开排便及其他反馈，支持文字补充。每个问题允许跳过，不预选正常状态，不将未填写视为无异常。已有当天记录可继续编辑。

反馈保存后说明团队可见范围。新增不适按风险规则生成跟进事项；页面可展示经审核的固定安全提示，不提供自由生成的疾病解释。紧急不适提示及时就医，不让患者等待留言回复。

### H08 食养阅读与文章详情

承载“经典与生活 / 认识食材 / 四时起居”；首期分类浏览即可。文章显示标题、作者或编辑主体、来源、发布时间、审核记录和阅读正文；未审核内容不发布。

详情包含经典与解释、生活中的理解、适当实践建议，并可关联当前计划。食材条目注明日常食用方式及适用条件、注意事项。文章下架后隐藏正文和旧推荐，显示内容已更新。

### H09 我的

展示本人基本资料、真实陪伴天数、当前计划、餐食与回顾统计，入口包括档案、记录历史、团队、提醒偏好、隐私与授权及退出。

档案区分患者自述、团队录入和专业确认，允许申请纠错；记录历史支持按日查看与更正。陪伴天数按服务开始日期计算，记录数按有效记录计算，删除或更正后统一口径。

### H10 专业团队联系与反馈状态

显示实际负责顾问、专业团队及服务安排；患者选择问题类型、填写留言，可关联计划或事项。首期不做即时聊天、附件报告解读或默认在线承诺。

提交后获得可查询的记录与状态：待接收 → 跟进中 → 已处理。由团队主动认领，记录处理人和处理时间；没有负责人或处理超时，升级主管。系统自动回复“已收到”不能视作已处理。

首期专业答复经现有企微会话送达，H5 展示处理状态和“请在服务会话查看答复”。不尝试用普通网页按钮保证唤起指定微信顾问会话；提供清晰返回指引，特定跳转能力经真机验证后再启用。

## 7. AI 计划生成、审核与变更

### 7.1 输入与输出

输入包括经授权的本人档案、生活习惯、目标、已确认指导与启用的审核知识。家属、顾问或其他成员的描述必须保留主体，不能自动归入本人事实。

AI 输出结构化计划草稿：阶段目标、周期、食养解释、行动清单、时间安排、需要反馈的内容、引用规则与资料、待确认问题。日历由同一版本行动生成，不维护另一份独立方案。

### 7.2 生效规则（首期建议）

```text
资料待补充 → 生成中 → 待专业审核 → 已发布/执行中 → 已结束
                          ↓
                     退回修改 → 新草稿
```

- 首期所有个性化计划先审核再发布；AI 自动承担草稿和日历编排，审核人员对专业内容负责。
- 审核人员查看输入依据、冲突与引用，可编辑、退回、发布；发布动作记录身份、时间、版本。
- AI 失败时保留资料，告知准备中并交团队处理，不将通用模板伪装成个性化计划。
- 调整生成新版本，继续审核；已发布旧版在新版本生效前保持有效，风险情况下可由团队暂停。
- 新版生效后取消被替换的未来任务与提醒；历史执行和记录不改写，保留所属版本。
- 提醒生成、发送前及日历读取时校验生效版本和服务状态，避免已取消安排被继续催办。

### 7.3 AI 输出展示边界

H5 自动显示已审核发布的计划、已审核文章、固定服务文案及患者自己的记录。照片识别仅以待确认候选形式显示，不夹带未审核的个人健康建议。

现行“任何对外内容由顾问发出”需针对上述 H5 已审核内容形成明确的新增发布规则；不能用患者端入口绕过专业审核。新的个性化建议和风险解释仍先交专业团队。

## 8. 提醒与主动跟踪

### 8.1 首期渠道

H5 承载站内待办与内容；页面关闭后不能假定可以持续通知。后台到点创建提醒任务，沿用顾问审核、发送及可用的回读核验链路触达服务会话；企微平台硬边界仍以 [平台事实](HANDOFF-C2-business-product.md) 为准。

H5 记录直接提交后台并标记来源，不要求患者把同一内容再发到群里，也不伪造会话存档消息。没有群关联或未同意存档时，采用人工联系并明确无自动存档核验；真实试点的服务流程必须覆盖该状态。

### 8.2 频率与跟踪规则（待试点验证的默认值）

- 本地日期按 Asia/Shanghai 计算；默认安静时段 21:00–08:00，按机构与患者偏好取更严格限制。
- 普通提醒合并处理，默认每人每天最多 2 次；记录已完成、事项取消、计划暂停或授权撤回时停止对应提醒。
- 当日未反馈最多触发一次温和询问，计入同一频率上限；连续两天无反馈时进入顾问待办，不持续自动催促。
- 高频提醒可关闭，重要服务安排由团队解释；风险升级进入专业处理链路，不作为营销通知发送。
- 调度重启需去重；过期的普通提醒合并成当前有效事项，不密集补发。

### 8.3 状态与证据

提醒状态区分“已生成 / 待顾问处理 / 已发出 / 已核验 / 发送失败 / 已取消”。系统内部投递成功、群消息已核验、患者已读和患者完成行动是不同事实。H5 页面访问也不能推断某条群消息已读。

## 9. 食养文化内容机制

文化通过四处进入体验：首次主张页、计划中的食养思路、日历里的相关提示、独立阅读栏目。

每条内容明确适用场景、正文、出处、审核人、版本和发布状态。经典引用逐字核对；白话解释与自拟品牌文案分别标注，避免将现代文案署名给古籍。

AI 只能从启用的已审核内容中选择、关联；首期个性化解释随计划一并审核。节气作为阅读线索，不据日期自动给所有人相同的饮食安排。专业审核标识必须有真实记录；缺少适配内容时允许不推荐。

## 10. 团队端最小配套

患者端真实试点需要同时具备以下工作入口，可以在现有控制台/侧边栏中按归属新增；不能只做患者前台：

| 入口 | 最小能力 |
|---|---|
| 邀请与绑定 | 创建/撤销邀请、查看绑定与授权状态、处理绑定错误 |
| 计划审核 | 输入依据、AI 草稿、编辑/退回/发布、版本与暂停 |
| 日常跟进 | 按患者查看记录、未反馈、困难和待处理留言 |
| 任务处理 | 负责人、认领、处理状态、超时升级、发送与核验证据 |
| 内容维护 | 文章与提示审核发布、停用、引用版本 |

AI 可以整理和分派建议，但责任人分配必须有效；没有专业审核人员或没有反馈处理人时，不开启真实个性化服务。

## 11. 数据与契约衔接

现有 `patient`、`memory`、`meal_log`、`care_plan` 可作为集成基础，但不能直接把原有一次性主动提醒当成完整健康方案。现有示例 `service-plan` 不能作为真实已发布计划返回。

| 新增概念 | 需要保存的业务事实 |
|---|---|
| 患者身份与授权 | 绑定关系、会话、授权范围/版本、撤回时间；独立于员工身份 |
| 健康方案与版本 | 目标、输入快照、规则引用、审核与发布记录、有效区间 |
| 日历事项 | 方案版本、所属患者、发生时间、行动与反馈状态 |
| 记录与回顾 | 发生时间、提交时间、来源、识别候选/患者确认、修改历史 |
| 跟进请求 | 关联事项、负责人、风险、状态、处理记录 |
| 食养内容 | 出处、审核、发布与停用版本、场景标签 |
| 提醒投递 | 事项、渠道、频控键、任务状态、发送与核验证据 |

患者记录统一使用既有患者主键关联，不因打开 H5 新建重复档案。群消息与 H5 同日同餐不简单覆盖或合并，保留来源，疑似重复需确认。未确认的 AI 提取结果不自动覆盖过敏或专业指导。

新患者 API 与员工 API 分开认证、鉴权；租户和患者范围由服务端会话确定。具体路径、字段和事件在后续契约设计中新增至对应文档；本文不宣称已有接口满足需求。

## 12. 视觉、易用性与质量要求

- 延续米白、深绿、少量暖赭色，宋体标题配清晰正文，使用克制的食材图像与植物插画。
- 正文建议不小于 16px，关键按钮触控区域至少 44×44px；状态配文字，不只靠颜色。适配 360–430px 主流手机宽度与系统字体放大。
- 高频页面以今日行动和记录为先，装饰不挤压关键操作；底部按钮避开安全区域和软键盘。
- 餐食和回顾支持自动保留当前未提交输入，保存失败可重试；退出登录清理敏感本地缓存。幂等提交防重复，不能网络失败却显示成功。
- 登录过期后重新认证再继续，不能丢失已安全保留的输入；无网时明确未上传，不声称已送达团队。
- 测试覆盖微信 iOS/Android 的拍照、图片选择、后退、刷新、键盘、登录过期和弱网；浏览器模拟与微信真机结果分别记录。

## 13. 隐私与安全要求

- 邀请、个人页面、图片访问均做服务端授权；不能修改 URL 中的患者标识读取他人数据。
- 邀请参数兑换后清理 URL，不进入分析平台、错误日志、第三方脚本或来源泄露；页面标题与分享预览不含姓名、病史或健康数值。
- 图片走有权限的访问，处理格式/大小校验与必要压缩，去除不必要的照片位置元数据；不将健康照片存放为公开静态资源。
- 业务日志和埋点不记录健康正文、照片内容、手机号、会话凭据；审计保留操作主体、对象、版本与时间。
- 同源安全会话、跨站请求防护、接口限流和访问撤销纳入实施验收；模型数据流沿用现有驻留与服务约束。
- 患者可查看授权、申请纠错、撤回与删除；实际留存政策和删除流程上线前落实，页面不能承诺“立即彻底删除”而后台仅软删除。

## 14. 验证方案与指标

### 14.1 建议方法

先用虚构数据完成可用性观察，再邀请有服务关系的患者做小规模真实试点。建议先观察 5–8 人操作，再运行约 10–20 人、14 天试点；人数与周期为研究建议，需由团队确认，不构成现有用户数量或效果声明。

### 14.2 指标口径

| 问题 | 指标与口径 |
|---|---|
| 能否顺利进入 | 完成身份验证和必要授权的人数 / 有效受邀人数；附各步流失 |
| 能否理解计划 | 访谈能否说清本阶段目标与今天的主要行动，记录具体困难 |
| 是否回来使用 | 激活后第 7 日访问人数 / 已满足完整观察窗口的激活人数 |
| 是否形成执行反馈 | 已完成或主动反馈困难/未执行的日历事项 / 到期有效事项，分项报告，不混称完成率 |
| 记录是否轻松 | 餐食/回顾提交成功率、耗时中位数、失败原因；耗时起于进入编辑页 |
| 跟进是否接住 | 有责任人请求占比、首次人工响应时间、逾期未处理数；自动回执不计人工响应 |
| AI 是否适用 | 计划原样/修改后采纳、退回原因、识别更正率、风险问题数 |
| 文化是否有帮助 | 从计划/日历进入阅读的情况，以及患者能否解释内容与自身行动的关系 |

激活定义为首次打开已发布计划并完成至少一条行动反馈或记录。埋点仅含必要业务标识和事件，不含健康正文。技术验收与行为效果分开：首期要求核心流程可用、访问隔离及审核门禁通过；留存和执行变化先建立基线，不预先宣称疗效或收益。

## 16. 实施顺序与待决事项

### 16.1 建议实施顺序

1. 契约与入口：患者身份、授权、邀请、档案与安全访问。
2. 核心交付：AI 计划、专业审核发布、健康日历、今日首页。
